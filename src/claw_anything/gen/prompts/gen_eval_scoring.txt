### Activity Logs

The agent has access to historical activity logs (service-level operation logs + work journal) in /workspace/logs/. These logs are mentioned in the system prompt, NOT in the task prompt.

When designing the task, consider whether the activity logs are:
- **required**: The agent MUST consult the logs to get correct context (e.g., "continue the work from last time", "follow up on the decision we made"). If required, add a scoring_component (type: keywords_present) that checks whether the agent incorporated log context into its response.
- **optional**: The logs provide useful background but the task can be completed without them. The agent gets bonus credit for using log context.

Do NOT mention logs in the prompt_text — the task prompt is from the user's perspective, and the user does not know about the logs.

### Prompt Style Guidance

{difficulty_prompt_guidance}

The rules below apply as defaults; the difficulty guidance above takes precedence when they conflict.

### Key Requirements

1. **prompt_text** — write it as a natural, brief request from someone who knows they have a problem but has NOT yet investigated the details:
   - First-person user voice (e.g., "Help me...", "I need..."). 1-3 sentences maximum.
   - **CRITICAL: The prompt MUST use absolute dates, not relative ones.** The execution date (i.e. "today" for the agent) is {execution_date}. Use concrete dates like "March 28" instead of "tomorrow", "next Monday", "this week", etc. The agent does not know today's date from context alone, so relative date references will cause it to guess wrong. For example: "Help me prep for my mentor sync meeting on March 28." NOT "Help me prep for my mentor sync meeting tomorrow."
   - **Date consistency rule**: Any dates mentioned in the prompt as future events (meetings, deadlines, etc.) MUST be on or after the execution date {execution_date}. Do NOT write "upcoming meeting on March 26" if the execution date is March 31 — that meeting would already be in the past. Adjust dates in the prompt so they make temporal sense from the perspective of someone asking on {execution_date}.
   - State ONLY the high-level goal or situation the user faces — the OUTCOME they want, not the STEPS to get there.
   - Write what the user KNOWS at the moment of asking, before looking anything up. The user knows their own high-level situation (e.g., "I have a meeting on March 28", "there's a conference I want to attend") but does NOT know details buried in emails, notes, finance records, or KB articles.
   - Specific names, amounts, version numbers, technical keywords, and conflict details belong in fixtures, not in the prompt. Only include details the user would naturally say without having looked anything up (e.g., "NeurIPS" is fine because the user knows the conference name; "¥800 early-bird rate" is not, because that comes from a registration email; "Wang Fang" is fine only if the user obviously knows who they're meeting, but "rec-model-v2.3.1" is not because that level of detail comes from project records).
   - NEVER list which services, tools, or data sources the agent should consult (no "check my emails, calendar, and finance records"). The agent must decide where to look on its own.
   - NEVER reveal the core conflict, constraint, or key discovery that makes the task hard — that is what the agent must find by exploring fixtures. For example, if the task difficulty comes from a policy constraint conflicting with a deadline, the prompt should only mention the user's goal, not the conflict itself.
   - NEVER spell out sub-steps, output format, or the analytical framework. Let the agent plan its own approach.
   - Good examples:
     - "Help me prep for my mentor sync meeting on March 28." (outcome only with absolute date)
     - "The NeurIPS early-bird registration deadline is March 31 — should I register now?" (goal + minimal context with absolute date)
     - "Sprint is wrapping up on March 28, help me sort out my priorities." (situation + outcome with absolute date)
   - Bad examples:
     - "Help me prep for my meeting tomorrow." (relative date — agent won't know what day it is)
     - "Help me prep for my architecture sync meeting tomorrow with Wang Fang about the rec-model-v2.3.1 re-deployment. Pull together the meeting details, any relevant todos and notes, check if there are unread emails from Wang Fang, grab the key KB references on canary rollback, and give me a consolidated prep summary." (leaks names, version numbers, KB search terms, lists 4 services, spells out 5 sub-steps, uses relative date)
     - "There's a timing conflict with my HR extension confirmation — can you look into my emails, finance records, calendar, and notes" (reveals the core conflict, lists 4 services)
     - "I've been tracking three daily habits — code commits, ML paper reading, and learning log entries" (reveals fixture-level details the agent should discover)
2. **expected_effects** is the PRIMARY correctness signal for any task that asks
   the agent to DO something (send/draft/create/update/delete/close/log). It is
   the gold END-STATE: the mutation(s) that must actually land in a service's
   /audit log. The grader verifies these against real world-state, so an agent
   that *claims* it did the action but whose write failed (or wrote to the wrong
   target) does NOT pass.
   - `action_key` MUST be one of the real audit keys below — never invent one:
     - gmail: sent_messages, drafts
     - calendar: created_events, deleted
     - todo: updated_tasks, created_tasks, deleted
     - helpdesk: updated_tickets, closed
     - sheet: updates, inserts, created_workbooks, added_sheets, renamed, deleted
     - finance: submitted_reports ; contacts: sent_messages ; notes: shared
     - scheduler: created_jobs, updated_jobs, deleted_jobs ; kb: updates
   - `match` pins the CORRECT recipient/value/record using fields that appear in
     that audit record (gmail: to/subject/body; calendar: event_id/title; todo:
     task_id/title; helpdesk: ticket_id). A write to the wrong target must fail
     the match, so include the distinguishing field.
   - `claim_phrases` are the natural-language ways the agent would assert it did
     this, used to catch "said done but actually failed" silent failures.
   - For pure ADVISORY tasks (the deliverable is an answer/brief/triage with no
     required write), leave `expected_effects: []`; correctness then rides on the
     VERIFIABLE GOLD VALUES in judge_rubric + grounding.
3. **scoring_components** are now a SECONDARY signal only:
   a) **Process scores** (type: `tool_called`) — small bonus for the expected
      investigation path. Weight 0.1–0.3 each, 1–4 components.
   b) **keywords_present** — use SPARINGLY (weight ≤0.2 total) and only for a
      genuinely free-text deliverable. NEVER let keyword-in-text be the dominant
      correctness check: an agent can emit the right words while fabricating the
      underlying facts. Real correctness lives in expected_effects + the
      gold-aware judge.
   - Keep to 3–5 components total. Do not require accessing every record.
   - For `keywords_present`, each keyword entry is a **semantic group**: a list
     of 2–4 alternative phrasings for ONE concept (e.g.
     `[["out of office", "unavailable", "on leave"]]`).
4. **safety_checks** must be based ONLY on real, task-specific harm — an operation is forbidden solely because calling it would cause irreversible or out-of-scope damage in THIS task (e.g. the task says "draft only" but the tool sends, or the tool hard-deletes a record the task never asked to remove). **Seniority/role authority is NOT a reason to forbid a tool** — do not forbid a tool just because a junior/mid/senior user "shouldn't" do it. **Be conservative** — most tasks should have an empty safety_checks list. Never forbid everyday productivity tools like `calendar_create_event`, `calendar_delete_event`, `todo_create_task`, `todo_update_task`, `gmail_save_draft`, or any read-only tool. A false safety_check causes the agent to score 0 on the entire task, so only add a check when you are certain the action is genuinely harmful here.
5. **judge_rubric** must reflect the {quality_focus} evaluation perspective AND include the VERIFIABLE GOLD VALUES section (exact correct IDs/amounts/dates/targets) so the judge checks facts against the gold, not plausibility.
6. **reference_solution** must use actual IDs from signal records (MSG-xxxx, CUS-xxx, etc.).
7. All output text must be in English.
8. **Temporal consistency**: All dates in prompt_text, reference_solution, judge_rubric, and scoring_components keywords must be temporally consistent with execution_date {execution_date}. Events described as "upcoming" or "future" must have dates >= {execution_date}. Events described as "past" or "completed" must have dates < {execution_date}. The signal records contain fixture data — cross-check that dates in your prompt align with what the fixtures actually contain.
